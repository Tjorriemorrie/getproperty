## Project

Property scraper. Python 3.13.1, managed with `uv` (see `pyproject.toml` + `.python-version`, `.venv/` in-tree). Django project `getproperty/` with a single app `main/` registered in `INSTALLED_APPS`.

A public-facing browse UI lives in the same app: `main/urls.py` registers `listing_list` (home, `/`) and `listing_detail` (`/listing/<listing_id>/`) in `main/views.py`, rendered by templates in `main/templates/main/` (`base.html`, `listing_list.html`, `listing_detail.html`, plus `_card_grid/list/compact.html` partials). The project `getproperty/urls.py` `include`s `main.urls` at `/` and serves `MEDIA_URL` in `DEBUG`. Frontend is Tailwind CDN + Google Fonts (Fraunces display, Inter body), Alpine.js for the layout toggle, and Swiper.js for the detail gallery — no build step.

`listing_list` is a thin orchestrator over module-level helpers in `main/views.py`: `ListingFilters.from_query()` (dataclass of parsed filter state), `_apply_filters(qs, filters, skip=)` (builds per-filter `Q`s via `_filter_conditions()`; a facet passes its own key as `skip` to count its options), `_resolve_ranges()`, `_percentile_facet()`, `_build_facets()` (checkbox facets from the `CHECKBOX_FACETS` table + In-a-complex/Liked radio counts), and `_decorate_listings()` (the `display_*` card attributes). To add a checkbox facet, add a `ListingFilters` field, a condition in `_filter_conditions()`, and a `CHECKBOX_FACETS` row.

Range facets (Price, Floor size — the `RANGE_FACETS` table) are built by `_percentile_thresholds()` from percentiles of the *currently filtered* result set, rendered as ≤ / = / ≥ selectors per threshold. Because the thresholds move whenever any other filter changes, `_resolve_ranges()` re-snaps the selected bounds onto the new thresholds via `_snap_range()` (mutating `ListingFilters`) before anything else is counted or filtered — see the ranged-filter rule under Conventions. The two ranges depend on each other's bounds, so it iterates (max `RANGE_SNAP_MAX_PASSES` = 3) until a pass changes nothing, which also keeps each facet's rows consistent with the other's final bounds. The snapped values (not the raw URL ones) feed the filtering, the hidden `price_min`/`price_max`/`size_min`/`size_max` inputs, the other range's facet hrefs, and the saved filter cookie.

Duplicate listings from different agents can be linked via `main.models.ListingGroup`. Listings have a nullable `group` FK; the group has a `primary` FK to the Listing whose details represent the group on list pages. The list view filters to `Q(group__isnull=True) | Q(group__primary_id=F('id'))` so only one row per group is shown (facet counts follow). Users toggle selection via a link icon on each card (persisted in `localStorage` via Alpine) and POST to `main:mark_similar`, which creates or merges groups. The detail page shows a numbered switcher of group siblings when present.

Free-text `notes` live on both `ListingGroup` and `Listing`. The detail page's `set_notes` endpoint (debounced 2s autosave via Alpine/fetch) writes to `group.notes` when the listing is grouped (so all duplicates share one note) and to `listing.notes` otherwise. The list view sets `l.display_notes` by the same rule and cards render it under the price/address block.

A boolean `is_liked` mirrors the same group-or-listing pattern — toggled from a switch above the notes input on the detail page via `set_liked`, and exposed as a 3-way Liked facet (Any / Liked / Not liked) below Price on the list page. `mark_similar` merges via `_target_group()` (lowest existing group id, else a new group) and `_merged_group_state()`: notes are de-duplicated in order, and `is_liked` is AND-merged (disliked dominates — any disliked source makes the group disliked); the listings' own `notes`/`is_liked` are then reset to `''`/False.

A `main_image` FK on both `ListingGroup` and `Listing` (pointing to a `ListingImage`, `SET_NULL`) overrides the card thumbnail used on the list page. The detail-page Swiper has a star button on each slide that POSTs to `set_main_image`; the button is disabled when the active slide already matches. Stored on the group when grouped (so any sibling's image can represent the group), otherwise on the listing. The list view annotates `l.display_image` (group main → listing main → first image) and the `_card_*.html` partials render that. `unlink_similar` clears `group.main_image` if it belonged to the unlinked listing; `delete_listing` is auto-handled via the FK cascade chain (image CASCADE on listing → SET_NULL on group.main_image).

`Listing.complex_name` (hand-entered sectional-title complex; `''` = not set) deliberately does **not** follow the group-or-listing pattern: it lives only on `Listing` and is copied onto every member of a group, so it survives `unlink_similar`/`delete_listing` untouched and filtering is a plain column lookup on the shown primary. `set_complex_name` normalises via `_normalize_complex_name()` (collapse whitespace; fold onto an existing spelling case-insensitively) and writes to the listing plus all group siblings; `mark_similar` picks the primary's name (else the first member's) and copies it onto all members, logging a warning on conflicts. The detail page renders it as an editable tile using `<input list>` + `<datalist>` of all distinct names, saving on `change`. The list page has a `complex` checkbox facet (via `_facet_checkbox.html`, under In a complex) whose first row is the `COMPLEX_NOT_SET` sentinel (`__none__` → `complex_name=''`); cards prefix the address line with the name. The scraper never writes this field.

`Listing.is_complex` (bool, default False) follows the same copy-to-every-member pattern as `complex_name`: `set_is_complex` writes the listing plus all group siblings, and `mark_similar` OR-merges it via `_sync_group_is_complex()`. On the detail page a vertical Alpine switch (`complexEditor()`, knob up = on) shares one `col-span-2` row with the Levies tile (`—` when `levies` is null) and the Complex name tile; both tiles render only while it's on (server-side `style="display: none"` + `x-show`, no `x-cloak` in `base.html`). Turning it off keeps the name. The scraper sets it only on create (`_save_listing`'s `create_defaults`, `levies > 0`), never on update/recheck. The list page's 3-way **In a complex** radio facet (Any / Yes / No; URL param `is_complex`, `COMPLEX_YES_Q`/`COMPLEX_NO_Q`) filters on this field alone — there is no levies filter any more. It replaced the old "+ Set placeholder" button that stored `levies=1`; migration `0015` flagged `levies > 0` listings (plus their group siblings) and nulled the 137 `levies=1` placeholders.

Scrapers live in `main/<source>.py` (e.g. `main/privateproperty.py`) and are invoked by a matching management command in `main/management/commands/scrape_<source>.py`. Listing/photo data is stored in `main.models.Listing` and `main.models.ListingImage`; downloaded photos land under `MEDIA_ROOT` (`media/listings/YYYY/MM/`). Scrapers use botasaurus's `@request` decorator with `parallel=N` for concurrent detail/image fetches. `walk_list_pages()` always walks **every** list page of a search (never stop at the first known listing — featured older cards are interleaved among the newest on page 1) and returns `(cards, complete)`; `_keep_base_query()` must be applied to each next-page link because the site's `?page=N` links drop the date sort and pages 2+ would otherwise be in a different order. `scrape()` fetches details only for cards not in the DB (all cards with `--all`) and returns the walk's `live_ids` + `complete`. See the README's "privateproperty.co.za findings" for the site quirks.

Removal detection is list-driven: when every source's walk was `complete` (i.e. no `--max-pages`), the command calls `reconcile_with_live(live_ids)`, which re-fetches active listings absent from all list pages (to confirm removal) and removed listings that reappeared (to restore them). Then, for non-`--all` runs, `recheck_oldest()` re-fetches the 1% (rounded up) least recently looked-at active listings, ordered by `Coalesce(rechecked_at, first_seen_at)` — don't order never-rechecked rows first: new listings arrive faster than the 1% budget, so the rotation starves and rechecked listings never come up again (that's how 670 removed listings went unnoticed). Both go through `_recheck_rows()` → `_fetch_recheck()` → `_apply_recheck_result()`, which returns `(outcome, images_saved)`. The recheck never destroys data unless availability is confirmed: a listing's `removed_at` is stamped to the recheck time (without touching its fields or images) when the response is HTTP 404/410, contains the removed marker (`REMOVED_MARKER_RE` — the ref is wrapped in `<strong>`, so the regex allows tags around it), OR the parse yields no usable text (no title, price text, or headline) or no image URLs. Any other HTTP ≥ 400 counts as a failed fetch and leaves the listing untouched. Only when the parse is clearly a live listing are fields overwritten and the image set replaced (rotation only — the reconcile passes `replace_images=False` and tops photos up via `_download_listing_images`, because the few live listings outside the searched suburbs, e.g. ones moved to Birdwood Estate, come up on every run) — and `_replace_listing_images` pre-fetches all new image blobs into memory first, only deleting the existing `ListingImage` rows once at least one replacement was downloaded successfully (so a transient empty fetch can't wipe good photos). `Listing.removed_at`, `Listing.rechecked_at`, and `ListingGroup.removed_at` track this; an unset `removed_at` means the listing is still active. Group cascade is centralized on `ListingGroup.refresh_removed_at()` — `removed_at` is set to the latest member `removed_at` iff every listing in the group is removed (cleared otherwise), recomputed in the recheck loop and on `mark_similar` / `unlink_similar` / `delete_listing`. Card templates render a "Removed" badge on the image when `l.display_removed_at` (annotated in `listing_list`) is set — that is `group.removed_at` for a grouped listing and `listing.removed_at` otherwise, so a group with at least one still-active sibling never shows the badge even when the primary itself is removed. After sorting, `listing_list` splits the results into `active_listings` and `removed_listings` (by `display_removed_at`); the template renders the removed ones in their own "Removed" section after all active cards (POA included), via the shared `_listing_section.html` partial, so they still honour every filter; the active section follows the chosen sort, but the removed section is always ordered by `display_removed_at` descending (most recently removed first, chosen sort on ties). Cards show "Removed X ago" under the "Listed X ago" line.

The detail page shows the active-listing duration above the title — "Active for X (since DATE)" while live, or "Removed · Active for X (DATE removed)" once `removed_at` is set (computed in `listing_detail` from `listed_at`/`first_seen_at` to `removed_at`/now). It also has a "Delete listing" button at the bottom that POSTs to `delete_listing` — removes only that `Listing` (cascading its `ListingImage` rows after deleting their files). The `ListingGroup` is preserved as long as any sibling remains (repicking the primary if needed and calling `group.refresh_removed_at()`); the group is only deleted when the removed listing was its sole member. This differs from `unlink_similar`, which dissolves a group as soon as only one sibling is left.

## Commands

- Scrape privateproperty.co.za: `uv run python manage.py scrape_privateproperty [--max-pages N] [--all]` (`--max-pages` skips the reconcile; `--all` skips the rotation)
- Run dev server: `uv run python manage.py runserver`
- Migrate: `uv run python manage.py migrate`
- Django management: `uv run python manage.py <cmd>`
- Add dependency: `uv add <pkg>`
- Sync env from `pyproject.toml`: `uv sync`

## Conventions

- Ranged filters (price, floor size, and any added later) must survive a change to another filter. Their options are derived from the currently filtered set, so applying another filter shifts the range and the selected bound stops matching any rendered option — the filter then looks unselected while it is still narrowing the results. Whenever a range's options are recomputed, re-snap the active selection onto the new options (nearest equivalent: a ≥ row, a ≤ row, or an = band) and use the snapped value everywhere downstream — filtering, the rendered selection, form inputs, links, and the persisted filter state — so the filter stays both applied and visibly selected.
- Never pin dependency versions in `pyproject.toml` (no `==`, `>=`, `~=`, etc.) unless the user has explicitly pinned them. After `uv add`, strip any version specifier it inserts so entries read as bare names (e.g. `"django"`, not `"django>=6.0.4"`). If the user has set a pin, preserve it.

## Pre-commit

`pre-commit` is a dev dependency (see `pyproject.toml`) with hooks defined in `.pre-commit-config.yaml` (ruff, plus core sanity/format checks).
